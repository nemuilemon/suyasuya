# PVT（反応時間テスト）の取り込み

**状態：案。未実装。**

## なぜ入れるのか

suyasuya が抱える構造的な問題がひとつある。
睡眠データだけを見ている agent は、**user がすでに知っていることしか言えない**。

「昨夜は 5 時間でした」——それは user も知っている。
スコアを提示するアプリが響かないのは、多くの場合これが理由だ。

PVT は、user が**原理的に自分では持てない情報**を agent に与える。

### 根拠

Van Dongen ら（2003）の実験。被験者を 6 時間/夜に 14 日間制限したところ、
注意・作業記憶の成績は日ごとに累積的に悪化し、最終的に「2 晩徹夜した人」に
相当する水準まで落ちた。

問題は次の点にある。
**本人の主観的な眠気は途中で頭打ちになり、それ以上悪くならなかった。**
彼らは「少し眠い」と感じながら、実際にはボロボロの成績を出していた。

つまり人間は、自分の劣化を自己申告で検出できない。
この隙間こそが、agent が声をかける正当な理由になる。

> 主観は平気だと言っているが、反応時間は 10 日下がり続けている。

これは睡眠時間の提示ではなく、**user が自力では到達できない観測**だ。
README の「agent が読んで、必要なときにだけ声をかける」を、
言えることの中身の側から裏打ちする。

## 「記録を求めない」と衝突しないか

README が退けているのは**睡眠そのものを記録させること**（記録が対象への注意になる）。
PVT が測るのは睡眠ではなく**日中の機能**なので、対象が違う。
「今日の集中力を測る」枠組みは、寝つきへの注意を増やさない。

ただし user への要求が 1 つ増えるのは事実。README には 2 本立てで書いた。

- 受動的な入力（screenshot）＝ 睡眠の記録
- 能動的な入力（PVT）＝ 結果の計測

## 何を測るか

標準の PVT は 10 分。長すぎるので **PVT-B**（Basner ら, 2011）を採る。

| | |
|---|---|
| 所要時間 | 3 分 |
| 刺激間隔 (ISI) | 1〜4 秒のランダム |
| 課題 | 画面にカウンタが現れたら、できるだけ速く反応する |
| lapse 判定 | 355 ms 超（標準 PVT の 500 ms ではない） |

記録する指標：

- **median RT** —— 中央値。外れ値に強い
- **lapse 数** —— 355 ms を超えた回数。睡眠不足に最も鋭敏
- **slowest 10% の平均** —— 崩れ方の裾を見る
- **false start 数** —— 刺激前に押した回数（焦りの指標）

単発の値には意味がない。**傾向線が読めて初めて使える。**

## 運用上の制約

計測条件を揃えないとノイズに埋もれる。

- **毎日ほぼ同じ時刻**に打つ（起床後の一定時間が望ましい）
- カフェイン摂取の前後どちらかに固定する
- 同じデバイス・同じ入力手段（キーボードなら常にキーボード）

この制約は agent 側が通知でかなり吸収できる。
「届くべき時刻に届ける」という既存の役割の延長に置ける。

## 実装の重さ

PVT 自体は**軽い**。canvas とタイマーと乱数だけで、推論もモデルも要らない。
screenshot の読み取り pipeline より明らかに安い。

想定するデータの形：

```
session: 打鍵日時 / device / 反応時間の配列
derived: median_rt / lapses / slowest10_mean / false_starts
```

生の反応時間配列は捨てずに持つ。指標の定義を後から変えられるようにしておく。

## 着手順への影響（重要）

**PVT のデータには lead time がある。コードにはない。**

傾向線が意味を持つには 2 週間分ほしい。**agent loop より先に、雑でいいので
記録部分を立てて打ち始める。** seed した偽データの曲線と、
実際に積み上がった曲線では説得力が違う。
