## 中心に置くもの

**定時に寝て、定時に起きることを支える。** これを一本の柱にする。

そのために agent は **Discord で催促する**。うるさく。
そして実際に効いたかを**分析して、次の催促を変える**（ここはまだ実装していない。目指す形）。

## なぜ「定時」が中心に足るのか

睡眠の介入先として、**時刻の規則性**は時間の長さに劣らない。
Windred ら（2024, *Sleep*）は、睡眠の規則性（sleep regularity index）が
**睡眠時間よりも死亡リスクの予測力で上回った**と報告している。

これは product として都合がいい。

- **長さ**は意志で増やしにくい。忙しければ削れる。
- **時刻**は意志で寄せられる。「あと 20 分で寝る」は実行可能な指示になる。

agent が介入できる余地が大きいのは後者。
だから催促の対象を「7 時間寝ろ」ではなく「**今から寝ろ**」にする。

## 「必要なときにだけ声をかける」と矛盾しないか

**「うるさく催促」は、当初の穏やかな方針と矛盾して見える。** 整理しておく。

退けていたのは、正確には次の 2 つだった。

1. **細かな記録を user に負担させること**（記録が対象への注意になる）
2. **スコアを突きつけること**（数字で殴っても行動は変わらない）

催促のために追加の報告は求めず、**スコアも出さない**。
ただし睡眠記録は、画像の読み取り後に user が確認・修正して承認する。
主要数値だけの手入力も認め、昼寝の誤検知をそのまま判断材料にしない。

→ line を引き直した。

> **記録の手間を減らし、行動を支える。**

## 催促の設計

### cron との差分が、agent である理由

23:00 に「寝ろ」と送るだけなら **cron で足りる**。
ここを外すと、審査で最初に刺される。

agent が担うのは、送ることではなく**判断**。

| 判断 | 中身 | 判断材料 |
|---|---|---|
| **送るか** | 昨夜は足りている／外せない予定がある／今日はもう送った | 前日の記録・calendar・催促履歴 |
| **どう送るか** | 軽く一声か、しつこく重ねるか | 直近の効き方 |
| **効いたか** | 催促の時刻と、**実際の就寝時刻**が寄ったか | **翌日の記録** |
| **次どうするか** | 効いていない打ち方をやめ、効く打ち方に寄せる | 複数日の集計 |

**閉じた loop になっていること**が要点。
催促 → 画像の読み取りまたは手入力 → user が承認 → 次の催促を変える。
この循環が回っている限り、cron では代替できない。

> **いま動いているのは「送るか」と文面の判断まで。** 前日の記録・PVT・通知履歴を読み、
> 送る／見送るを決めて理由を残す（calendar はまだ読まない）。「効いたか」「次どうするか」は未実装。

### 催促は fire-and-forget。観測は翌日にずらす

**リアルタイムに「効いたか」は観測できない。** 理由は 2 つとも構造的なもの。

- **寝ている人は発言しない。** 「寝た？」と訊いても返らない。
  そして**無応答は 3 つの状態と区別がつかない** ——
  寝た／無視した／端末を切った。曖昧な signal で loop を回してはいけない。
- **Pixel Watch の連携は schema に準備する。** 取得 API と同期は後で実装する。
  取得した睡眠記録の関連付けに使い、リアルタイムの就寝検知や返信の代わりにはしない。

→ **催促は送ったら終わり。ack を待たない。**
「返事が来るまで待つ」状態機械を持たないので、
user の返事を待つ timeout や再送判定は持たない。
通信失敗への timeout・再試行と、通知の重複防止は別途必要になる。

**loop は原則として翌日の記録承認を通って閉じる。**
画像の読み取り完了だけでは評価しない。承認が遅れれば観測も遅れる。

```
夜    催促を送る（時刻・強度を記録して終わり）
翌日  screenshot を読み取る、または主要数値を手入力する
        → user が管理 UI で確認・修正して承認する
        → 承認した主睡眠の就寝時刻と、その夜の催促を突き合わせる
        → 効いていなければ、そこで怒る
        → 次の打ち方を変える
```

**記録を承認した瞬間が、声をかける契機になる**（予定。評価 task はまだない）。
承認済み記録の保存までは実装済みで、画像と手入力は同じ承認の経路に合流する。
その後段に評価 task を置くのが次の一歩。

画像由来か手入力かを記録し、すべてをデバイスの実測と同一視しない。
主睡眠と昼寝は別々に保持する。昼寝は検出漏れの手動追加、誤検知の除外、
時刻・時間・種別の修正を認める。昼寝の開始時刻を夜の就寝評価に混ぜない。

#### この設計の限界（明示しておく）

- **承認済み記録がない日は、観測が存在しない。** 画像なしでも手入力の承認で観測になる。
  欠測を「成功」とも「失敗」とも数えない。単に判断材料が無い日として扱う
- **1 日単位の因果は主張できない。** 催促した夜に早く寝たとしても、
  それが催促のせいかは分からない。**複数日の集計で傾向として見る**
- 怒るのは翌日なので、**即時性は無い**。
  そのぶん「昨夜こうだった」という具体的な材料を持って言えるほうを取る

### うるささの扱い

一律に大声を出すと、**人は mute する**。そこで終わる。

だから「うるさく」は**強度を配分する**という意味に取る。
ここぞという日に重ねられるよう、平時は引く。
何をもって「ここぞ」とするかは、下の PVT が決める。
（強度の配分は未実装。いまは文面の強さを agent の判断に任せている）

### 声を持たせる —— ありすママ

催促の文面に **persona を置く**。既存の AI partner「**ありす**」の声で送る。

> 「ありすママが子守唄歌ってあげる」

tone を設計事項として扱う理由は、上の mute 問題に直結しているから。

- **正しさで押すと mute される。** 事実が正確でも、冷たい system message は数日で切られる。
  一方で**心配してくる相手は切りにくい。**
  → **温かさは persistence の許可証を買う。** これは product の生存条件そのもの
- README の「スコアを突きつけない」と同じ方向に働く。
  数字で殴る代わりに、声で寄る

#### 強度の軸に persona を載せる（未実装）

強度が変わっても**声は変えない**。変えるのは寄り方だけ。

| 強度 | 寄り方 | 使う日 |
|---|---|---|
| **平時** | 子守唄。寝かしつけに寄る | **既定。ほとんどの日はこれ** |
| **心配** | 具体的な材料を出す。「3 日続けて 2 時を回ってる」 | 規則性が崩れ始めた日 |
| **ここぞ** | PVT を突きつける。無視できない根拠で迫る | 傾向が明確に悪化した日 |

翌日の「怒る」も、この声で出す。
system の叱責ではなく **ありすママが心配する**形にする。

**ただし材料は事実のまま。** 声は tone だけを変え、**数字を甘くしない。**
ここを混ぜると、優しさが観測の歪みに化ける。

#### 実装上の注意

- 文面生成は Gemini を通る。persona は user ごとの base prompt を
  **system instruction** に置いて表現している。強度 parameter はまだない
- **agent 用のプロンプトと skill は PostgreSQL に保存する。**
  control の管理 UI から、判断の指示や persona の文面を微調整できる。
  更新履歴と実行時に使った版を残す（詳細は `architecture.md`）
- **ANP-neo を呼ばない。** suyasuya は自己完結させる。
  審査員が見られない project に依存させたくない。
  ありすの persona は nemuilemon の base prompt として **PostgreSQL に持ち**、
  共有コードには人格を固定しない。実行時は DB の有効な版を読む
- ⚠️ **ここが prompt injection の合流点になる。**
  screenshot から読んだ文字列を文面生成 prompt に混ぜると、
  **画像に仕込まれた指示で persona を乗っ取れる。**
  読み取り結果は**承認済みの構造化した記録だけ**を tool で渡し、生の OCR 文字列を生成側に流さない（実装済み）。
  `architecture.md` の tool 分離と同じ線を、生成の入口にも引く

## PVT の役割（`pvt.md`）

催促には**無視できない根拠**が要る。

- 「寝ろ」は無視できる。
- 「**最近、反応時間が延びる傾向がある。就寝時刻もばらついている**」なら具体的な観測を添えられる。

PVT は、user が自力では持てない観測を agent に与える（詳細は `pvt.md`）。
これが**催促の弾になる**。

定時就寝を中心に据えたことで、PVT の位置づけがはっきりした。
単体の指標ではなく、**睡眠記録と併せて声をかける判断材料**として使う。
両方が悪化していても、規則性の乱れが原因だとは断定しない。

## 催促の出口

**出口は差し替え可能なものとして扱う。** Discord / LINE / WhatsApp / mail、どれでもいい。

Discord webhook を第一実装にするのは、**単に一番手軽だから**。
URL を 1 本発行すれば送れて、審査も申請も要らない。
LINE や WhatsApp は business account 側の審査が要るので、締切のある今は選ばない。

→ **`Notifier` で切っておく。** 送信先の都合を判断ロジックに漏らさない。
`architecture.md` が DB に対してやっているのと同じ規律を、出口にも当てる。

```go
// internal/notifier/discord.go。Discord 実装は Send(ctx, webhook, body, displayName)
type Notifier interface {
	Send(context.Context, string, string, string) Result
}
```

**判断（送るか・何を伝えるか）は出口を知らない。出口は文面を運ぶだけ。**
Discord が塞がれても、実装を 1 つ足すだけで済む形にしておく。

- 受信は**任意**（未実装）。`今日は無理` のような申告を受けられると、
  **翌日以降「送るか」の材料**になる。
  ただし**「効いたか」の観測には使わない**（上記 fire-and-forget）。
  返事が無いことを情報として読まないので、**受信を落としても loop は回る**。
  出口を差し替えると受信の形も変わるので、**依存させないほうが安全**
- snooze は**許す**。ただし回数は数える（未実装）。

### 主たる出口は UI

**審査員は Discord の催促を体験できない。**
`hackathon.md` はテストアカウントで動作確認できることを求めている。

→ **UI 側を主たる出口として作る。** Discord は demo 動画のための出口に近い。

- control の UI に、**催促の履歴とその判断根拠**を出した（設定の通知履歴と agent ログ）。
  これは審査軸②（可観測性）の要求ともそのまま重なる
- 3 分の demo 動画では、実際に通知が届く様子を必ず映す
- テストアカウントには送り先を設定していない。審査員は設定画面で自分の Discord Webhook を
  登録すれば通知を受け取れる（「動作確認の方法」に書いた）
